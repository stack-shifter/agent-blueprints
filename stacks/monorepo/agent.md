## Project shape

Multiple packages in one repository, each with its own manifest and its own tests. Shared
code lives in its own package, not in a grab-bag `utils` directory. Read the workspace
manifest first to learn what the packages are and how they depend on each other.

## Toolchain

- Install once at the root. Never install inside a package directory.
- Run tasks through the workspace runner, not by changing directory into a package.
- Scope work to the packages you touched rather than running the whole repo every time.
- Never edit a lockfile by hand. It is generated at the root and covers every package.

## Package boundaries

- A package imports another only through its published entry point. Never reach into a
  sibling's internal paths.
- Adding a dependency between two packages is a design decision — ask before creating a
  new edge in the graph.
- No circular dependencies. If two packages need each other, the shared part belongs in a
  third.
- A change to a shared package affects every consumer. Before changing one, find the
  callers and say in your summary which packages are affected.
- Keep a change within one package when you can. A pull request touching many packages
  needs a reason stated up front.

## Versioning and release

- Version bumps and changelog entries are generated by the release tooling. Never hand-edit
  a version field.
- Never publish, tag, or release without being explicitly asked.
